- 修复逐字歌词「整句完全不亮」：YRC 字标签的绝对时间被重复叠加了行首时间。
  - 做了什么：NeteaseMusicApi.parseYrc 的字起点由 `行首 + 字标签` 改为直接取字标签的绝对时间（仅当小于行首时才按相对偏移补上行首，兼容个别源），与 YRC 规范 `[start,duration](start,duration,0)Word` 一致；MusicMetadataCache 新增 `repairLegacyWordStarts`，解析增强 LRC 缓存后修复历史上被写坏的字起点：字起点晚于下一行起点（末行则晚于行首×2）即落在本行区间之外、不可能成立，回退减去行首还原；数据正常时不改动任何内容。
  - 踩坑：①这个 bug 被原实现的「整行时长按词数均分」渲染方式掩盖了——那时渲染根本不读 `word.startMs`，一旦改成按字时序渲染就整句不亮，属于改动暴露的存量缺陷。②歌词缓存按增强 LRC（`<mm:ss.xxx>`）落盘，写坏的绝对值已存在于用户设备上，只修解析对旧缓存无效，必须同时做读取侧修复。③修复判据必须带 `nextLineStart > line.timeMs`，否则重复时间戳的行会被误判并被改坏。
  - 验证：./gradlew :app:compileDebugKotlin、./gradlew :app:assembleDebug 均 BUILD SUCCESSFUL。

- 修复逐字歌词未按字/词自身时序渲染（原先按「整行时长 ÷ 词数」均分）。

  - 踩坑：①当时误判了语义：以为 `NeteaseMusicApi.parseYrc` 的 `start + 字标签`（=绝对）是对的、缓存路径的 `<mm:ss.xxx>`（绝对）也对，实际前者才是错的（见上方条目）；渲染层只需按绝对时间比较，两侧时间基准必须一致。②歌词缓存按增强 LRC 序列化（`<mm:ss.xxx>` 只有起点、无时长），回读时 `durationMs` 必为 0，故「下一个词起点兜底」不是可选优化而是必需路径；词起点本身能完整保留，卡拉OK效果不受影响。

  - 做了什么：MusicPanelLyrics.kt 新增纵向拖拽调进度。①滚动位置改为普通状态 `scrollPosition`（浮点行号）承载：正常播放由跟随动画 `animate(...)` 推进，拖拽时由手势直接写入，释放后的吸附/回弹也写同一状态——用普通状态而非 Animatable，避免释放瞬间读到过期动画值导致内容闪回拖拽前位置。②新增 `LyricScrollGeometry`（普通对象，非 Compose 状态），由 LyricColumnLayout 测量时写入窗口起点与各行实测高度；手势按「像素 ÷ 当前行到下一行中心的距离」换算行位移，行高不定也 1:1 跟手且不触发额外重组。③中线固定基准标识（左右两段短横线，形如「- 歌词 -」，仅拖拽时淡入），拖拽中高亮中线最近的候选行作为选中反馈。④释放判定：`|位置 - round(位置)| ≤ 0.35 行` 则吸附到该行并 `seekTo(lines[i].timeMs)`；否则不跳转进度，以 `spring(DampingRatioMediumBouncy)` 弹性回弹到拖拽前位置。⑤手势用 `detectVerticalDragGestures` 声明在 `combinedClickable` 之后（内层），过 slop 后 `consume`：拖拽取消点击，且不触发外层左右滑动切面板；点按/长按不受影响。⑥全程不暂停、不改播放状态，只有对齐释放那一刻才 seek。

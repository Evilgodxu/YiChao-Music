# MVVM + 分区架构 · 架构约定

本文档为强约束共识，随架构演进评审修订。
目录组织仅为参考示例，见同目录《目录组织参考》。

## 数据流

单向数据流（Unidirectional Data Flow）：
状态自上而下流动，事件自下而上传递。
状态只能从 UiState 一处读取；行为只能经由 ViewModel 公开方法进入。

## 分层模型

```
data/      数据层：数据来源与实现（MediaStore / OkHttp / DataStore 等）
domain/    领域层：业务接口与模型（歌词、播放列表、在线搜索等）
ui/ + screens/   界面层：Compose 界面
service/   播放核心：唯一的播放服务（前台服务 + 通知栏控制）
```

依赖单向：screens → domain / data 接口，禁止反向依赖。

播放器本体只在 PlaybackService 中创建；其余代码一律通过全局播放接口访问播放状态，只读不改。
播放状态（播放 / 进度 / 队列 / 曲目信息）为单一事实源，被多个页面复用时上提至全局，页面不得另持一份。

## 状态管理约定

- 每页一个不可变 UiState（data class），ViewModel 以 StateFlow<UiState> 对外暴露。
- UI 以 collectAsStateWithLifecycle() 订阅。
- 事件模型：
  - 页面内交互 → ViewModel 公开方法（onPlay() 等），内部更新状态；
  - 跨页动作（起播、跳转）→ 统一走全局播放接口与导航，禁止跨页直连他人 ViewModel；
  - 不引入额外 Event / Intent 通道，保持低复杂度。
- 状态恢复：
  - 页面级业务状态存 SavedStateHandle；
  - 短暂输入状态（搜索框文本等）用 rememberSaveable；
  - 数据类结果状态由 ViewModel 持有，随实例存续即可。

## 布局分层原则

- 由窗口尺寸类（WindowSizeClass）分发 compact / expanded；旋转仅是触发场景之一（分屏、折叠屏展开同样触发）。
- 每页状态与逻辑只存在一份（页面级），与形态无关；compact / expanded 只负责同一状态的不同演绎。
- 两形态布局一致的内容不进分区，放 component/。
- 副作用（加载、播放等）不在 Area 内触发，上提至 ViewModel / 页面级。

## 通用上提，专用下沉

- 被两个及以上页面复用的模块（overlay/、service/、dialog/、domain/、ui/ 等）上提至对应顶层；
- 仅单个页面使用的，保留在该页面目录内。
- 上提以实际复用为准，不为未来复用提前抽象。

## 依赖管理

- 显式声明：所有依赖显式声明，经 Koin 构造注入；禁止隐式依赖、禁止在组件内手动 new 数据源。
- 完整限定导入：所有导入使用完整限定名，禁止通配符（*）导入。

## 命名与资源

- 分区命名 = 语义 + Area（如 TitleArea），Area 表示界面功能分区。
- 文案统一经 stringResource 引用，禁止硬编码。
- 颜色与主题统一经 theme 管理，禁止硬编码，除非设计如此。

## 视觉统一

- 新创建的对话框、开关、图标等使用方式必须与既有设计一致；同一项目出现两种圆角 / 间距 / 阴影风格的对话框，即视为违反约定。
- 优先复用与升级共享构件，禁止自造：
  - 对话框：一律经共享对话框基础构件（容器 + 标题 + 内容槽 + 按钮槽）拼接；确认、输入、加载等常规形态走参数化；
  - 交互控件（Switch / Checkbox / Slider 等）与图标：使用主题化封装控件与统一图标库（Material Symbols），尺寸与着色走 theme token，禁止混用图标集或硬编码颜色；
  - 弹层（对话框 / 遮罩浮层 / 悬浮窗）：共享弹层基础设施（遮罩、进场动画、定位、尺寸策略、关闭手势），内容一律经内容槽注入，不把具体内容塞进共享层。
- 出现新形态时：扩展共享构件（参数 / 槽）优先；类型不一致才独立实现，但仍须复用弹层基础设施与主题 token。
- 圆角、间距、阴影等视觉细节统一进 theme token，不散落硬编码。

## 工程规范

- 协程：耗时操作（IO / 网络）收敛在 data / domain 层；ViewModel 内使用 viewModelScope；UI 不感知线程调度。
- 三态：加载中 / 错误 / 空态使用顶层 ui/ 共享组件，不逐页自造。
- 测试：ViewModel 单测；Repository 以 fake 注入；Compose UI 测试；test/ 目录镜像主包结构。

## 代码原则

- 复用判定（按“本质是否一致”分层）：
  - 总纲：基本一致能复用就复用；类型不一致的独立处理，不因复用埋下“改 A 伤 B”的隐患。
  - 数据与逻辑一致 → 必须复用（上提），禁止复制；
  - 呈现基本一致、差异可参数化（行数、开关等） → 共享组件 + 参数传差异；
  - 类型不一致（渲染方式 / 交互结构不同） → 独立实现，仅共享下层数据与原子单元，不共享整块面板；
  - 共享粒度宁小勿大：共享到“数据模型 + 原子视图单元”，组合由各调用方完成；
  - 警示信号：组件内出现场景判断（if 3D / if 迷你播放器 / if 悬浮窗）即共享粒度过大，应向下拆一层。
- 宁要适度冗余，不要过度抽象；严防隐式耦合与“上帝类”。
- 模块边界清晰：改 A 不伤 B，删 A 不动 B。
